# verify-markdown-viewer

Markdown Viewer is a Manifest V3 browser extension that turns `.md` files into
rendered HTML. The user surface is the rendered page: the extension detects a
markdown document (by `text/markdown`/`text/plain` content type or by path
match against `.md` and friends), injects a content script, and replaces the
plain `<pre>` with themed HTML plus an embedded sidebar. Secondary surfaces are
the action popup (`/popup/index.html`), the options page
(`/options/index.html`), and a full-page reader (`/reader/index.html`).

There is no server and no CLI. Verification drives the real extension in a real
browser. Two hard facts shape the harness and are easy to get wrong:

- **Branded Google Chrome ignores `--load-extension` and
  `--disable-extensions-except`.** The extension must be loaded into *Chrome
  for Testing* (CfT). `scripts/launch.sh` resolves a CfT binary and fails
  loudly if none is found.
- **The checkout is only loadable after its build artifacts exist.** The repo
  git-ignores `manifest.json`, `themes/`, and `vendor/`; they are generated by
  `sh build/package.sh chrome`. The current working tree has them, so a plain
  launch works, but a fresh clone must run the build first. `launch.sh` fails
  with "extension failed to load" when they are missing, which is the signal to
  rebuild.

## Launch

Run from the repo root:

```bash
STATE=$(bash .omp/skills/verify-markdown-viewer/scripts/launch.sh)
```

This creates a fresh run dir `/tmp/mdv-verify-<ts>-<pid>/` with an isolated
profile, writes a `hello.md` fixture, launches CfT with the unpacked extension
loaded, waits for the debugging port, discovers the extension id, and writes
`<run-dir>/state.json`. It prints the state path. Two runs never share a profile
or a port, so instances run side by side.

If `launch.sh` prints "no Chrome for Testing binary found", set `MDV_CFT` to a
CfT executable path. If it prints "extension failed to load", run
`sh build/package.sh chrome` and retry.

`launch.sh` is the only entry point. There is no server to keep alive beyond the
CfT process it starts; the state file records its PID.

## Doctor

Before driving anything, or whenever the instance looks off, run the read-only
check:

```bash
bash .omp/skills/verify-markdown-viewer/scripts/doctor.sh "$STATE"
```

It answers "is this instance worth driving" by asserting, in order: the CfT
process is alive, the debugging port answers, an extension service-worker target
at `/background/index.js` exists, and that worker reports
`name == "Markdown Viewer"`, `version == "5.3.1"`, and file-scheme access granted.
All five checks must print `PASS` and exit 0.

## Drive

The harness is `scripts/run.mjs`, a Node CDP client. It attaches to the first
page target, navigates it to a URL, waits, evaluates JavaScript, and optionally
captures a screenshot. One invocation is one user step; chain invocations for
multi-step flows. The content script injects asynchronously after the tab loads,
so the default `--wait-ms 2500` (or longer) is required after navigating to a
markdown file.

Drive the primary feature, markdown rendering, against the fixture:

```bash
node .omp/skills/verify-markdown-viewer/scripts/run.mjs \
  --state "$STATE" \
  --url "file://$(python3 -c "import json;print(json.load(open('$STATE'))['fixtures'])")/hello.md" \
  --wait-ms 3000 \
  --eval 'JSON.stringify({ h1: document.querySelector("h1")?.textContent, sidebar: !!document.getElementById("__mdv_sidebar") })' \
  --shot "$(python3 -c "import json;print(json.load(open('$STATE'))['artifacts'])")/render/hello.png"
```

Assert on the rendered DOM, never on `window.state` (that variable lives in the
content script's world and is not visible from the page). Stable handles:

- rendered headings: `document.querySelector("h1")`, `"h2"`, and the anchor
  child `h1 .anchor`;
- the sidebar root: `#__mdv_sidebar`, its tabs `#__mdv_tab_files`,
  `#__mdv_tab_outline`, `#__mdv_tab_search`, `#__mdv_tab_fav`;
- Prism highlighting: `document.querySelectorAll(".token")`;
- the active theme/color: `document.body.className` (expect
  `_theme-<name>` and `_color-light|dark`).

**Reload and re-navigation are safe.** The content script re-injects on a
second navigation to a markdown URL and on `Page.reload` (F5); the rendered
content persists across both. An instance can drive multiple markdown
navigations, so a fresh instance per feature is not required.

To drive the popup-backed features (theme switch, raw view), navigate to the
popup, mutate a control, then navigate back to the markdown file so the content
script re-injects with the new settings:

```bash
EXT_ID=$(python3 -c "import json;print(json.load(open('$STATE'))['extensionId'])")
# switch theme to water-dark via the popup's first <select>
node .omp/skills/verify-markdown-viewer/scripts/run.mjs \
  --state "$STATE" --url "chrome-extension://$EXT_ID/popup/index.html" --wait-ms 1500 \
  --eval '(() => { const s = document.querySelector("select"); s.value = "water-dark"; s.dispatchEvent(new Event("change", { bubbles: true })); return s.value })()'
# load the markdown file once and observe the theme class
node .omp/skills/verify-markdown-viewer/scripts/run.mjs \
  --state "$STATE" --url "file://$FIX/hello.md" --wait-ms 3000 \
  --eval 'JSON.stringify({ theme: document.body.className })'
```

The feature map in `features/` gives per-feature entry points, commands, and
observable end states.

## Evidence

Proof artifacts live in `<run-dir>/artifacts/` (printed in `state.json`). Each
proof must show the action and the resulting state, not just a final screen:

- A screenshot per assertion (`run.mjs --shot`) with the rendered content and
  the sidebar visible.
- The `run.mjs` stdout `eval` field carrying the literal DOM values the feature
  asserts (heading text, token count, theme class, raw-vs-rendered).
- For a mutation (theme switch, raw toggle), capture both the before control
  and the after state, and reopen the markdown file rather than trusting the
  popup's own label.

Exercise the real user path: theme and raw go through the popup controls, not
through `chrome.storage` setters. Screenshots are full-page PNGs; keep them in
`artifacts/<feature>/`.

## Cleanup

```bash
bash .omp/skills/verify-markdown-viewer/scripts/cleanup.sh "$STATE"
```

It kills the PID recorded in `state.json` (never by process name), removes the
scratch `profile/` and `fixtures/` directories and `chrome.log`, and leaves
`artifacts/` untouched. Confirm the evidence still exists after cleanup before
declaring the run finished. Run this after every failed iteration too, so a
broken attempt does not strand a process or a port.

## Helpers

All scripts are executable and live in
`.omp/skills/verify-markdown-viewer/scripts/`:

- `launch.sh [--port N] [--run-dir DIR]` — launch an isolated CfT instance and
  print the state file path. Env `MDV_CFT` overrides the browser binary,
  `MDV_REPO` overrides the checkout path.
- `doctor.sh <state.json>` — read-only health check; exits 0 only when all
  checks pass.
- `run.mjs --state <s> --url <u> [--eval <js>] [--shot <png>] [--wait-ms <ms>]`
  — drive one tab step; prints a JSON verdict.
- `cleanup.sh <state.json>` — teardown that preserves `artifacts/`.
